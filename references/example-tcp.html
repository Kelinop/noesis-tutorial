TCP 三次握手：为什么必须是三次

两条消息无法让双方都相信「对方收到了」；第三次不是礼貌，是双向确认的数学下界。

2026-08 · 计算机网络 · 阅读 ≈ 18 MIN · 范围声明：以单连接建立为例；拥塞控制 / 窗口管理 / 重传定时器不展开

01PROB. 原始问题 · PROBLEM

01两次握手的失败：确认本身需要被确认

TCP 在不可靠的 IP 之上提供可靠字节流。建立连接的第一件事是互相确认：「我想连你」「我同意」——两句就够了？不够。第二次消息（SYN-ACK）到达客户端之后，客户端才知道服务器同意；但服务器无法知道客户端是否收到了这句同意。如果 SYN-ACK 在网络里被延迟或丢失，客户端会重发 SYN，服务器会收到重复请求；更糟的是，一条多年前延迟到达的旧 SYN（Tomlinson 1975 年描述的经典问题）会骗服务器分配资源。

问题是双向的：每条「确认」本身都需要被确认，而这条「对确认的确认」又需要被确认——直接递归下去没有尽头。工程压力很明确：在不可靠信道里，最少需要几条消息，才能让双方都确定连接建立？

两条消息无法让双方同时确认——服务器的资源会花在死连接上。
本质 · ESSENCE

数学下界：三次是必要条件，不是惯例

02

TCP 的三次握手不是约定俗成，而是双向确认的数学下界：第一条让服务器知道「客户端想连」，第二条让客户端知道「服务器同意」，第三条让服务器知道「客户端收到了我的同意」。两条不安全——服务器会把资源分配给无法确认的连接；四条冗余——第三条之后双方都已确定，第四条不再传递新信息。

这个模型的断裂点在「消息可能重复」：握手保证的是「此刻双方状态一致」，不保证「后来的每条数据都被送达」——数据可靠靠序号与重传，那是握手之外的另一套机制（见页头范围声明）。

03MECH. 机制 · HANDSHAKE

03SYN → SYN-ACK → ACK：状态机怎么转

三条消息对应两次「角色翻转」（见图 1）：客户端先发 SYN（初始序号 seq=x），服务器回 SYN-ACK（自己的初始序号 seq=y，同时确认 x+1），客户端最后回 ACK（确认 y+1）。第三次之后，双方各自持有一组「对方的确认号」，连接建立。

误解 · 「两次就够」

客户端发 SYN，服务器回 SYN-ACK，客户端收到后自己心里有数了——凭什么还要再发一条 ACK？服务器收到 ACK 与否，连接不都已经能用了吗？

正解 · 服务器是信息少的那一方

客户端收到 SYN-ACK 后确实确信连接建立；但服务器只知道自己发出过 SYN-ACK，不知道它有没有被收到。如果 SYN-ACK 丢失，客户端重发 SYN，服务器会分配第二份资源；如果旧 SYN 延迟到达，服务器还会为早已结束的连接再分配一次。第三次 ACK 让服务器把「已分配资源」与「客户端确实在等待」对上号——资源分配必须等确认，这是可靠性的前提。

把三次握手翻译成状态机的样子，客户端与服务器各自走一条状态链（见图 2）。注意服务器多出一个中间态：SYN_RCVD（半连接）——它已经分配了传输控制块，却还没等到客户端的最终确认。

SYN、ACK 这些旗标住在报文头里（见图 3）。头部的等宽排布本身就是规范：每个字段的位数是协议的一部分——这正是 ASCII 图而不是示意图的原因。

六个旗标各管一件事，拆开看（见图 4）：SYN 是「开始」，ACK 是「确认」，FIN 是「结束」。三次握手只踩 SYN 与 ACK；拆除走 FIN——这也是为什么拆除需要四条消息：两个方向各需一次 FIN + 一次 ACK。

易错 · 三个高频陷阱

① 第三次 ACK 不带数据。它只是一条确认，但它不是「白发的」——没有它，服务器永远停在 SYN_RCVD。② SYN flood 攻的是半连接：攻击者只发 SYN 不回 ACK，服务器 SYN_RCVD 占满监听队列，正常客户端进不来。③ 三次握手 ≠ 双方同时就绪：客户端在发出 ACK 时已就绪，服务器要等收到 ACK 才就绪——两者差一个 RTT 的「感知差」。

两次握手：资源悬置

SYN-ACK 丢失或延迟时，服务器无法区分「客户端没收到」与「客户端放弃了」。旧 SYN 到达 → 服务器分配资源 → 客户端根本不在等待 → 资源变成死占用。服务器的确认闭环是开的。

三次握手：闭环闭合

第三条 ACK 把「服务器发出的同意」闭环。此后任何一条消息丢失都能被对端的重传兜住：客户端重发 SYN，服务器重发 SYN-ACK。确认链是闭合的，死资源不再可能产生。

第三次不是礼貌，是双向确认的数学下界——少一次不安全，多一次冗余。

04TRAD. 权衡 · TRADEOFF

04可靠性的租金：每个连接先付一个 RTT

三次握手用「每个新连接一次往返」换来了「建立过程不需要任何状态回收机制」。对长连接这是小钱；对请求-响应式的短连接（一次 HTTP 请求一条连接），握手延迟可能超过数据传输本身。

这笔租金促生了整整一代「0-RTT」方案：TCP Fast Open 用 cookie 让后续连接跳过握手，QUIC 把加密与传输握手合并——它们不是推翻了三次握手的逻辑，而是把「已经验证过的对端」缓存起来，省掉重复验证。第一次连接仍然是三次握手，数学下界没有被绕过，只是不再每笔交易都付。
