TCP 三次握手：双向确认的数学下界

为什么面向连接要从三次握手开始：不可靠的 IP 层、双向确认的下界、序号与重传、四次挥手——每次消息数都不是惯例，而是约束的必然。

2026-08 · 计算机网络 · 阅读 ≈ 35 MIN · 范围声明：TCP 经典模型（RFC 793 语义），握手/挥手消息数为「双向确认的数学下界」论证

01PROB. 原始问题 · THE PROBLEM

01IP 层只保证尽力而为：丢包、乱序、重复都是日常

TCP 建立在 IP 之上，而 IP 是尽力而为的服务：报文可能丢失、可能乱序、可能重复到达、可能被延迟很久后重放。应用层需要的是「字节流可靠交付」——一个字节不多、不少、不错、不乱。这两者之间的鸿沟，就是 TCP 存在的全部理由：在不可靠的信道上，用编号、确认与重传造出可靠的抽象（见图 1）。

问题

发送方不知道报文是否到达；接收方不知道下一个来的是哪个；双方都不知道对方的状态。

压力

网络既不保证送达也不保证顺序（IP 无状态）；但应用（文件传输、HTTP）必须拿到完整正确的字节流。

方向

先建立「双方都确认对方活着且愿意通信」的连接——而建立连接本身也要对抗丢包：需要多少条消息才够？

问题不在丢包本身——在「没有一种可靠的方式让对方知道我知道」。
本质 · ESSENCE

本质钩：三次是双向确认的数学下界

02

连接 = 双向确认：客户端要确认「服务器活着」，服务器也要确认「客户端活着」。一条消息只能承载一个方向的信息——客户端发 SYN 证明自己存在，服务器回 SYN-ACK 同时确认客户端并宣告自己存在，客户端再回 ACK 确认服务器。三次之后，双方都确认了对方的确认。一次太少（服务器不能确认客户端），两次不够（客户端不能确认服务器的确认），四次多余（第三次 ACK 已经完成双向闭环）。

这个模型的断裂点：三次握手只能确认「双方可达且愿意通信」，不能防止 SYN 延迟重放——这正是第 06 节半连接攻击的根源。下界解决的是「最少需要几条」，防重放需要的是另一套机制（随机初始序号 + 时间戳）。

03HANDSHAKE 机制 · HANDSHAKE

03三次握手：谁先说话，各自确认了什么

客户端主动打开（active open），服务器被动监听（passive open）。三条消息、四个语义动作——第三条 ACK 同时是「客户端对服务器 SYN-ACK 的确认」，不需要第四条（见图 1）。

04WHY 3? 误解 · MISCONCEPTION

04两次握手会发生什么：一个真实的重放场景

反对意见很自然：「客户端发 SYN、服务器回 ACK，不就互相确认了吗？」——错在服务器的 ACK 没有被确认。看这个真实场景：客户端连接 1 的 SYN 在网络中延迟，客户端超时重试连接 2 成功并传输完毕、正常关闭；此时延迟的 SYN 到达服务器，服务器以为新连接到来，分配资源并回 ACK——但客户端根本不知道这个连接存在，服务器为一个死连接分配了资源（见图 4）。

常见误解：「两次握手就够了——客户端发 SYN，服务器回 ACK，连接就建立了。」
工程现实：服务器的 ACK 无法确认。延迟的 SYN 重放时，服务器会为一个不存在的连接分配资源。第三次 ACK 不是礼仪——它是 双向确认的下界：让服务器知道「客户端知道我在线」。
追问：「那四次握手不是更安全？」
工程现实：四次对双向确认是冗余的——第三次 ACK 之后，双方的确认链已经闭合：客户端确认服务器（SYN-ACK）、服务器确认客户端（ACK）。四次只是重复第三次的语义。一次太少，两次不够，三次是下界，四次多余。
易错 · 第三次 ACK 不能携带数据？

第三次 ACK 可以携带数据（TCP 允许捎带）——「三次握手要等确认再发数据」是错的；真正的语义是「第三次 ACK 发出后，客户端侧确认链闭合」。面试写「第三次 ACK 后双方才 ESTABLISHED」时，注意状态迁移是收到第三条才算数。

05RELIABLE 机制 · RELIABLE TRANSFER

05编号 · 确认 · 重传：在不可靠信道上造可靠

连接建立后，数据面用三件套对抗不可靠：seq 编号（每个字节一个序号，重排的基础）、累积确认（ack = 期望的下一个字节号，隐含「之前全部收到」）、重传（超时重传 + 快速重传）。走一遍真实场景：客户端发 3 个报文，第二个丢失（见图 5）。

BLUEPRINT CALLOUT · 滑动窗口

窗口 = 允许未确认的最大字节数：发送窗口 = min(接收方通告窗口，拥塞窗口)。窗口让「等确认再发」变成「流水线发送」——吞吐量从 RTT 分之一提升到窗口/RTT，代价是内存与丢包后重传的代价变大。

06CLOSE 机制 · CLOSE & ATTACK

06四次挥手与半连接洪泛：关闭也要双向确认

关闭与建立对称：连接是双向的，每一方向独立关闭。A 发 FIN（我不再发送）、B 回 ACK（收到）、B 发 FIN（我也不再发送）、A 回 ACK——四个方向性动作，所以是四次（见图 7）。中间的 ACK 与 FIN 可以合并（B 无数据待发时），三次挥手是合法优化，不是新的下界。

易错 · SYN flood 与半连接队列

SYN flood：攻击者只发 SYN 不回 ACK，服务器为每个 SYN 分配半连接（SYN_RCVD）占满队列——后续正常连接全被拒。防御：SYN cookie（不分配资源，用序号编码状态）。考试问「为什么两次握手更容易被攻击」——两次握手时服务器在第一条消息就分配资源，三次握手也只在 SYN-ACK 后暂存，真正的资源分配推迟到 ESTABLISHED。

07TRADEOFF 权衡 · TRADEOFF

07可靠的代价：一次握手多一跳，一个连接多一份状态

面向连接买到的是可靠与有序，付出的是三笔账：建立延迟（三次握手至少 1.5 RTT 才能发数据，UDP 首包即发）、每连接状态（发送/接收窗口、序号、缓冲区——服务器受限于连接数）、队头阻塞（一个段丢失，后续有序数据全部等待重传）。这就是为什么短小请求（DNS）选 UDP、长流与可靠性要求（HTTP/文件）选 TCP（见图 8）。

08408 真题演练 · WORKED EXAMPLES

08常考问答：从握手到挥手的一问一答

Q1 · 为什么是三次而不是两次？

双向确认的下界：第三次 ACK 让服务器确认「客户端收到了我的 SYN-ACK」。两次握手在延迟 SYN 重放时会为死连接分配资源（见图 4）。答「防半连接」不够精确——准确说法是「服务器侧确认链无法闭合」。

Q2 · seq 初始值为什么随机？

防延迟重放与序号猜测：固定的初始序号让攻击者能伪造在途报文；随机 ISN + 时间戳让旧连接的延迟报文无法冒充新连接的数据（RFC 793 要求初始序号随时间变化）。

Q3 · 快速重传与超时重传的区别？

超时重传依赖 RTO 定时器（慢，且 RTO 估算困难）；快速重传收到 3 个重复 ACK 立即重发，不等待超时（见图 5）。代价：重复 ACK 需要接收方「缓存乱序段」配合——这是接收窗口存在的另一层理由。

Q4 · TIME_WAIT 为什么是 2MSL？

MSL = 报文最大生存时间。主动关闭方等 2MSL：保证最后一个 ACK 如果丢失，对方重发的 FIN 还能到达（一来一回 2MSL）；同时让在途报文死透，避免与复用同一四元组的新连接串扰（见图 7）。
